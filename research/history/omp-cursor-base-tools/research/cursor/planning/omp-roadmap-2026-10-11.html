Полные результаты без обрезок и перечитываний

Уже есть
  • read отдаёт файл целиком, если в нём меньше 100 тысяч символов и 90 КБ.
  • При обрыве read и grep пишут, с какого места продолжить.
Что меняем

Сейчас результат режется здесь:

список glob5 000 символов
дерево папки2 500 символов
строка в grep1 000 символов
чтение документов omp49,6 КБ
строка в документах omp и ответах субагентов512–768 символов
вывод eval7,8 КБ
длинный ответ субагентапревью
  • Один бюджет до 100 тысяч символов на любой результат.
  • Дерево: все папки видны всегда, файлы — пока хватает бюджета, а большая папка сворачивается в строку «N файлов, такие-то типы».
  • Общий бюджет на один ответ, чтобы пачка параллельных чтений не переполняла окно и не вызывала сжатие.
  • Ни одной молчаливой обрезки: полный результат сохраняется, а строка обрыва говорит, как получить остаток.
  • Неудачная правка показывает ближайшее совпадение с номерами строк, и файл не нужно перечитывать перед повтором.

Базовые инструменты не слабее Cursor

Уже есть
  • omp выполняет вызовы одного ответа одновременно. Фоновых задач может быть до 100, а запросы к провайдеру по умолчанию не ограничены.
  • Редкие инструменты лежат под xd:// и выдают описание по запросу, как GetDynamicTools и CallDynamicTool в Cursor.
  • Поиск в rg.ts работает на нативном движке omp, а он собран и для Mac, и для Windows.
  • Встроенный bash omp работает одинаково на Mac, Linux и Windows, у него свои grep, sed, find и jq.
  • omp пишет ОС и архитектуру в промпт, а skill omp-tools задаёт вид путей: /Users/... на Mac, C:/... на Windows.
Что меняем
  • Функции не слабее базовых инструментов Cursor: Shell, Glob, rg, ReadFile, ApplyPatch, AskQuestion, GetDynamicTools и CallDynamicTool, у субагента ещё UpdateCurrentStep. Имена и дополнительные функции свои.
  • Поисковые инструменты видны сразу. В этой сессии grep, lsp, find и ast_grep пришли позже, по запросу. Редкие инструменты остаются по запросу.
  • Ввод прощает ошибки: путь в любом виде, шаблон без **/, regex с неэкранированными скобками.
  • На выходе везде один формат путь:строка, его можно сразу подать в следующий вызов. Ошибка называет причину и точное исправление.
  • Путь в любом виде (/c/Users, C:\Users, C:/Users, ~) приводится к одному. В промпте одна строка: ОС, оболочка, вид путей и доступные программы. Windows проверяем отдельным запуском.
  • 10–50 вызовов в одном ответе без лишних очередей.
Сейчас eval, write и todo выполняются по одному и задерживают остальные вызовы.

Субагенты поиска

Уже есть
  • codebase_explorer работает на Haiku 5.5 с reasoning high.
  • Main сам читает только известные пути и делает один поиск, остальное отдаёт explorer.
  • Main переиспользует свободного субагента: метка [task id#n] прячет от него прежнюю работу.
  • Хуки omp: tool_call может переписать вход вызова, а tool_result — заменить содержимое результата.
  • По твоим словам, окно Haiku — миллион токенов, а мы ограничили его 400 тысячами со сжатием около 270 тысяч.
Что меняем
Main ставит задачу→бриф: вопрос, где, глубина→explorer на Haiku ищет→полный ответ: факты, file:line, код→Main работает дальше
  • Explorer ведёт любой поиск, кроме чтения известного пути. Main только ставит задачу.
  • Бриф из трёх полей: вопрос, где искать и глубина. Как искать и что вернуть, записано в определении агента. Если нужна строгая форма, расширение подставляет шаблон через tool_call. Для поисковых агентов это заменяет правила skill subagent-brief.
  • Explorer отдаёт полный ответ на 7–8 тысяч токенов и больше, а этап 1 гарантирует, что он дойдёт до Main без обрезки.
  • Форма ответа: факты с file:line и дословные куски кода, которых хватает, чтобы Main не открывал файлы сам.
  • Отдельный веб-агент для внешней документации: .md-версии страниц и llms.txt. Документы внутри репозитория ищет агент для кода. Третий агент нужен, только если для документации появится свой механизм. MCP не используем: в репозитории они запрещены.
  • Если Haiku держит миллион токенов, explorer получает большее окно и порог сжатия. Иначе глубокий поиск делится на несколько explorer по областям.
  • Транспорт IRC оставляем, меняем только размер ответа.

Правила harness

Уже есть
  • Gold Standard и манифест требуют собирать минимум сведений, нужных для решения.
Что меняем
  • Кто ищет: Main читает только известный путь, всё остальное ищет explorer.
  • Когда поиск закончен: раунды идут по тексту, по связям через lsp, по структуре через ast_grep и по смыслу через find. Поиск заканчивается, когда раунд не приносит ни одного нового релевантного файла.
  • 99,9% проверить нечем, эталона нет, поэтому полноту задаёт это правило.
  • Для поиска правило «минимум сведений» меняется на «всё, что относится к задаче». Это правило Gold Standard и манифеста меняешь ты: skills/gold-standard/SKILL.md и WORKFLOW-CONCEPT.md правим только по твоему решению.
