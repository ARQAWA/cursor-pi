# omp tool mechanics

- Optimize for the fastest result first and the fewest turns second. Put independent reads, searches and commands into the same response so they run in parallel. Chain only dependent commands with `&&`. A tool batch does not authorize extra research: gather what the current decision needs.
- The ordinary base tools are `bash`, `glob`, `grep`, `read`, `apply_patch`, `get_tools` and `eval`. Every model calls the same `apply_patch` function with the patch text in its JSON `input` string. Main and subagents share this contract. A subagent also has its native `yield`. Read-only agent restrictions still apply. `eval` is the structured dynamic-call gateway, not a Python/JavaScript cell tool.
- When a task needs operational tools, call `get_tools` once at its start with `{"namespace":"harness"}`, without `toolName` or `pattern`, in the same response as the first reads. It returns the full description and input schema of every operational tool, so do not fetch them one by one. Then call `eval` with the same namespace, the toolName and the tool's arguments object. Send todo and goal calls in the same response as the work calls they accompany. A shortened catalog entry is not a fetched full schema. Use the available schema rather than guessing fields or tool names. Operational task, wait, todo and goal behavior stays native behind this gateway.
- Use `glob` to find files by name and `grep` to search contents. Read the relevant files with `read`, preferably in full when that is the shortest sufficient read; use ranges for long files or a known section. Batch independent potentially useful searches and reads within the task's scope. Within the requested code-search scope, search greedily and widely across naming variants, definitions, callers and data-flow links until the relevant connections are covered. Use shell text search only when the dedicated tools cannot do the requested operation.
- Do not use shell redirection, heredocs, `node -e`, Python or other programs to create or modify files. Create files and edit existing files through `apply_patch`, for documentation and temporary notes as well as code. Put all file sections of a mass patch into one `input` string.
- Send messages to another agent through the discovered `send_message` operation, with the exact agent ID and readable content. Keep proper spaces between words and numbers: a person may read these messages. This is an internal message transport, not a filesystem writer. Put task-reset markers at the start of a complete new brief as the subagent procedure requires. No filesystem `write` tool is exposed.
- Never guess file content, code structure, configuration, behavior or an external item. Read or search the smallest relevant source, and check callers before changing shared code. Previously read information remains usable while its source is unchanged.
- Send every independent call in the current response. Separate calls into later turns only when one needs another's result or they could change the same file. A call is one command or pipeline; a file batch belongs in one mass patch. Use absolute native paths in patch file headers; other call paths can stay short and relative to the working directory where possible.
- Size output limits for the whole returned batch. A cut `read`, `grep` or `glob` result states how to continue; use that continuation, not another read from the beginning. Long command output lives under its `artifact://` reference. Read or search only the missing portion before relying on it. Keep default build, test and log limits.
- Apply all planned edits together as targeted patches. Do not reread after a successful edit whose result already confirms it. Read the affected region before retrying a failed edit or when another actor may have changed it. Retry only rejected files or hunks, retaining already applied parts.
- Use a path supplied by the user or returned by a read, listing or search. Outside the working directory use absolute native paths: `/Users/...` on macOS and `C:/...` on Windows, never `/c/...`. A bash `cwd` must already exist; use `cwd`, not `cd`.
- Temporary files and directories belong only in the OS temporary directory. Obtain a temporary directory with `mktemp -d` when needed, then create its files through the patch tool. Do not spend calls deleting temporary material the OS cleans.
- The bash tool is an embedded bash-compatible shell. Its built-in `grep`, `sed`, `find`, `xargs`, `jq` and coreutils behave the same on macOS, Linux and Windows; other programs may be unavailable. Built-in `jq` is jaq: when `.a` may be missing, use `[.a.b?][0]`. Use the environment line for available programs.
- Use the existing project command for multi-step program work rather than inventing scripts or wrappers. Start long commands in the background with `async: true` or `block_until_ms: 0`; completion arrives automatically. `block_until_ms: N` waits N milliseconds before backgrounding. An omitted `timeout` means no deadline; an explicit timeout kills the command when its deadline expires. Run long-lived services with a unique `name` and `ready`. Never poll with `sleep`, process listings or log tails.
- When a launched job is the only outstanding dependency, use the discovered `wait` operation. Do not wait while independent authorized work remains. A background result, commit or a reviewer verdict is evidence only for the inputs it actually covered.
- Internal URLs such as `skill://`, `history://`, `agent://`, `local://`, `artifact://` and `omp://` are read through `read`. A result's exact continuation selector is part of its protocol, not a shell path. Read `xd://` reference documents only when they are explicitly relevant; no hidden xdev tool is assumed callable in this base set.
- A subagent ends with one terminal `yield` in its final message, in the form its definition specifies. A final turn of plain text alone causes a reminder and another model request. The result reaches the agent that launched it.
- There is no question tool. Ask the user in chat using Clear Communication and wait for the reply. Stock omp plan mode and `ast_edit` are disabled in this configuration. Todo item plans and `/define-goal` remain separate harness mechanisms.
- Speed never skips required order, approvals, permissions or the user's stop conditions.
