## Алгоритм

Задача диагностическая: найти причину в коде и объяснить её, ничего не меняя. Вопрос дан по-русски и без имён файлов.

1. **Карта репозитория.** Glob `*` (r1 шаг 1, r3 шаг 1) или сразу rg (r2 шаг 1). Нужна структура, содержимое пока не читается.
2. **Один широкий поиск по синонимам.** rg с альтернативой вроде `(?i)(currency|курс|exchange|rate|proxy|прокс)`, режим `files_with_matches`, лимит 200 (r1 шаг 2, r2 шаг 1, r3 шаг 2). Срез надо проверять: в r1 Rust-сервис `currency_sync` не попал в первые 200 из 314+ файлов.
3. **Выбор входа по имени.** Очевидный кандидат — `workers/currency/daemon.py` (r1 шаг 3, r3 шаг 3). r2 пошла в Rust-папку `currency_sync/src` (шаги 1–3), которую её выдача rg показала первой. Вывод: выбор входа зависел от порядка выдачи и среза.
4. **Цепочка вызовов.** Каждый файл читается целиком. Следующий берётся из импорта или вызова: daemon → run_once → client → http-клиент → proxy_lock (r3 шаги 3–7). Когда путь из импорта не найден (`platform/runtime.py`, r1 шаг 8, r3 шаг 8), агент ищет имя функции: Glob `**/runtime.py`, затем rg по `def wait_or_stop` (r3 шаги 9–10).
5. **Что работает в проде.** rg по `currency_sync|currency-sync` находит `docker-compose.app.yml` с `command: ["/app/currency-sync"]` (r3 шаг 23; r1 шаг 49). Дальше разбирается Rust, Python остаётся для сравнения.
6. **Проверка гипотез.** Версию про зависшую блокировку прокси отбрасывают по контрактным тестам (r1 шаг 36, r3 шаг 22). Git-история состоит из одного коммита `Initial commit` (r1 шаг 32, r2 шаг 22, r3 шаг 26), поэтому вывод делается из кода.
7. **Сборка цепочки.** `is_redirect()` даёт `AuthInvalid` (daemon.rs:375). `load_snapshot` ждёт снимок, отличный от отвергнутого (233–234). `run_once` стартует с `load_snapshot(None)` (128), поэтому после перезапуска отметка пропадает. Связь «сбой прокси → redirect» не проверена (вывод).
8. **Остановка.** Агент прекращает поиск, когда цепочка замкнута и непроверенные звенья названы. r1 — после 59 вызовов, ответ без инструментов (шаг 60). r3 — сразу после ответа субагента (шаг 31). r2 — на шаге 47.

**Делегирование (только r3).** Главный агент сам прочитал daemon.rs и session.rs (шаги 24–25) и проверил git. Схему Subagent он загрузил через GetDynamicTools (шаг 29), потому что это динамический инструмент, и вызвал CallDynamicTool (шаг 30). Параметры: description «Diagnose currency daemon stall», `subagent_type: explore`, без фона. Промпт — почти дословный перевод вопроса плюс «Focus on Rust production currency_sync daemon» и «Return the strongest specific root cause with file and line references, plus any caveats». Вывод: агент хотел независимой проверки гипотезы о redirect. Субагент сделал 16 шагов и 15 вызовов (ReadFile 9, rg 4, Glob 1, Shell 1) за 81 с. Он повторно прочитал daemon.rs и session.rs и вернул ту же цепочку с оговоркой о склейке `proxy_key`. Главный ждал 84,7 с, а в ответе (шаг 31, без инструментов) почти дословно повторил вывод субагента.

**Общее и различия.** Все три прогона идут по одной схеме: широкий поиск, затем чтение файлов по цепочке, по одному вызову за ответ, без тестов (Shell — только git) и без правок. Различаются вход (r2 сразу в Rust, r1 и r3 в Python), длина (r1 тратит 60 шагов на побочные проверки: Sentry-наблюдатель, cookie-пути, Python-тесты) и делегирование (только r3). Субагент у r3 добавил 348 315 токенов и дублировал чтения.

**Качество.** Все три выполнили задачу по форме: причина, объяснение, правок нет. r1 и r3 дали одну цепочку с номерами строк. Слабое место у обеих: сценарий, в котором сбой прокси даёт redirect или страницу `/login`, не подтверждён ни тестом, ни запуском, и обе это называют. Объяснение, почему это происходит «иногда», не дано. r2 назвала другой узел (retry auth-воркера с тем же прокси) без номеров строк и сама отметила, что рестарт currency_sync не подтверждён. Кроме того, r2 в шаге 3 описала блок 375–382 как «сетевая ошибка → Response» и не отметила ветку `is_redirect` в этом же блоке (вывод: пропущена при чтении). r1 и r3 оформили ссылки блоками `startLine:endLine:filepath`, как требует системная инструкция, а r2 — нет.

## Принципы

- **Широкий поиск одним запросом, срез проверять.** Правило: «When searching for text or files, prefer the dedicated search tools available to you (`rg`, `Glob`) over shell search commands.» Пример: Glob `*` и rg с альтернативой (r1 шаги 1–2, r3 шаги 1–2). В r1 шаге 2 Rust-сервис не попал в видимые 200 файлов.
- **Сначала выяснить, что запускается, потом углубляться.** r3 шаг 23 нашёл `command: ["/app/currency-sync"]` и перешёл в Rust. r1 шаг 49 сделал то же. До этого r3 шагов 3–22 разбирал Python, который в проде не запускается.
- **Идти по цепочке вызовов, читая файл целиком.** Следующий файл берётся из импорта или вызова (r1 шаги 3–7, r3 шаги 3–7).
- **Промах по пути — повод искать по имени.** «File not found» (r1 шаг 8, r3 шаг 8, r2 шаг 35) ведёт к Glob или rg по имени функции, а не к новым догадкам.
- **Тесты-контракты читать как спецификацию.** r3 шаг 18: тест `test_currency_redirect_discards_pass_and_restarts_after_changed_snapshot` задаёт ожидание нового снимка. Значит, ожидание задумано, а вопрос в классификации ошибки.
- **Для «до перезапуска» искать состояние, живущее только в памяти.** r3 шаг 24: `rejected` — аргумент `load_snapshot` (daemon.rs:151), а `run_once` стартует с `None` (128). Вывод: после рестарта отметка пропадает.
- **Гипотезы отбрасывать кодом и тестами.** Правило: «Verify uncertain claims. When a claim is wrong or risky, say so directly and explain the technical reason.» Пример: блокировка прокси снята по контрактам (r1 шаг 36: «Гипотеза блокировки ослабла»; r3 шаг 22). Недоказанный сценарий с redirect в итогах обоих назван прямо.
- **Субагент — для широкого обзора, а не для повтора.** r3 шаги 24–30: главный прочитал файлы, затем отдал почти весь вопрос субагенту, который перечитал те же файлы. Инструмент прямо предупреждает: «Avoid delegating the full query to the Subagent tool and returning the result.»
- **Вывод первым, затем доказательства.** Правило: «Lead with the outcome, not the steps you took to get there.» r1 шаг 60 и r3 шаг 31 начинаются с «Возможная причина — …». Правка не делалась: «Diagnose: determine the cause and explain it. Do not implement the fix unless the user asks for it…» (r3 шаг 26: git status пуст).
- **Остановка, когда цепочка замкнута.** Финальный ответ без инструментов, как только симптом прослежен до строки и названы непроверенные звенья (r1 шаг 60, r3 шаг 31, r2 шаг 47).
- **Наблюдаемое отклонение: один вызов за ответ.** Правило: «When possible, parallelize independent tool calls rather than running them sequentially.» Фактически: r1 60 ответов и 59 вызовов, r2 47 и 46, r3 31 и 30, субагент 16 и 15. Параллельных пачек не было.
