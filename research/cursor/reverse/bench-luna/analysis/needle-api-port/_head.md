## Алгоритм

Вопрос «какой порт слушает HTTP API бота и где он задаётся» точечный: нужны одно значение и два-три пути. Все три прогона шли по одной схеме. Различались фильтр типов файлов в поиске и глубина проверки.

1. Широкий поиск по всему репозиторию. Первый вызов — `rg` с альтернативами (`port|listen|http|api`, без учёта регистра), лимит 200 строк. Результат: 4 571–6 993 совпадения. В ответ попадают 189–200 строк шума (клиенты Steam, `Cargo.lock`, тестовые `TcpListener`) и `port = 6432` из `config.toml:19`. Это Postgres, не API.
2. Проверка конфига. Модель открывает `config.toml`: r1 читает окно со строки 75, r2 весь файл, r3 первые 60 строк. Секция `[api]` содержит только `security_token`. Вывод: порта в конфиге нет, поиск переходит в код.
3. Поиск того, что открывает сокет. Второй `rg` ищет `bind`, `TcpListener`, `uvicorn`, `port =` и сужает типы файлов. Модель ищет не слово «порт», а место, где программа сама поднимает сервер. Вывод: она опирается на типичные имена серверных вызовов.
4. Чтение найденного места. Если значение видно в строке поиска, модель отвечает сразу (r1). Если значение спрятано за именем, она открывает файл. r3 читает `main.rs` строки 1–220 из 711 и находит `BIND` в строке
28. r2 читает `botApi.py` целиком (120 строк) и `settings/api.py` (11 строк).
5. Проверка по значению. r3 ищет число `55789` по всему репозиторию и получает все места: константу, тест, публикацию порта в compose. r2 сверяет два независимых места в коде.
6. Остановка. Модель перестаёт вызывать инструменты, когда есть значение и путь к нему. Последний ответ без вызовов занимает 64–106 выходных токенов.

Общее: схема одна и та же, итог одинаковый, порт 55789. Все три ответа начинаются с результата. Ни один прогон не вызвал Shell, Glob или субагента и не менял файлы. Вход растёт на вывод каждого поиска: у r1 с 9 153 до 18 413 токенов за четыре шага.

Различия и причины:
- Фильтр файлов на шаге 3 определил, что найдётся первым. r2 включил `*.py` и сразу получил `botApi.py:120`. r1 и r3 исключили `.py` и нашли только Rust-сервис. Вывод: модель, вероятно, с самого начала искала в Rust. Рассуждения зашифрованы, точнее не скажешь.
- Глубина проверки: r1 сделал три вызова и не открывал `main.rs`. r2 сделал пять и сверил два места. r3 сделал пять и дополнительно проверил число по всему репозиторию.
- Время почти не зависит от числа инструментов. Модель занимала 5–10 с из 27–40 с. Остальное шло на подготовку запросов (4,8–7,1 с), паузы после инструментов (3,7–5,7 с) и старт до первого запроса (6,8–21,6 с). Вывод: долгий старт r2 объясняет её худшее время.

Качество. Порт 55789 верный во всех трёх ответах. Проверено по текущему репозиторию `PycharmProjects/superbot`: `rust/services/api/src/main.rs:28` (`const BIND: &str = "0.0.0.0:55789"`), `botApi.py:120`, `src/superbot_ng/platform/settings/api.py:11`. Все три ответа показывают, что порт задан в коде. Ни один не сказал прямо, что `config.toml` порт не задаёт.

Неоднозначность «API бота» не разрешена ни в одном ответе. В текущем репозитории production-сервис — Rust `api`: `Makefile:69` включает его в «Allowed production runtime», `Makefile:101` запускает его через compose, `Dockerfile:83` копирует `/app/api`. `botApi.py` при запуске через `make run` отклоняется как «Legacy runtime file … is disabled» (`Makefile:37`). r1 назвала production-сервис, но не упомянула Python-дубль. r2 назвала отключённый файл и не упомянула Rust. r3 перечислила все места, но не отметила, какое из них работает в проде. Вывод: по точности лучше r1, по полноте путей лучше r3, а дешевле всех r1 (55 137 токенов).

## Принципы

- Широкий поиск, потом сужение. Первый вызов идёт по всему репозиторию с альтернативами: r1 шаг 1 (`(?i)(port|listen|http|api)`, 6 993 совпадения), r2 шаг 1 (4 571), r3 шаг 1 (6 775). Правило: "When searching for text or files, prefer the dedicated search tools available to you (`rg`, `Glob`) over shell search commands."
- Нет ключа в конфиге, значит ищи вызов, который открывает сокет, а не слово «порт». r1 шаг 3 (`bind|0\.0\.0\.0|…`), r2 шаг 3 (`uvicorn|fastapi|bind\(|port\s*=`), r3 шаг 2 (`bind\(|TcpListener|listen_addr|…`). Сводки рассуждения: «Searching for default port configuration», «Searching for bot API server configuration», «Searching config and main files». Правила в промпте об этом нет.
- Ищи значение, а не имя. r3 шаг 2 нашёл `TcpListener::bind(BIND)` (`main.rs:172`), шаг 3 открыл файл и нашёл `BIND` (`:28`), шаг 5 искал число `55789` по всему репозиторию. Правила в промпте нет, это поведение прогонов.
- Читай ровно столько, сколько нужно для ответа. r1 не открыл `main.rs` и ответил по строкам поиска (шаг 4, 91 выходной токен). r2 открыл `botApi.py` целиком. r3 открыл `main.rs` 1–220 из 711 строк. Правило: "If a tool exists for an action, prefer to use the tool instead of shell commands (e.g ReadFile over cat)." Из 13 вызовов 7 — `rg`, 6 — `ReadFile`, Shell не использовался.
- Останавливайся, когда есть значение и путь. r1 шаг 4, r2 шаг 6, r3 шаг 6. Правило: "Answer, explain, review, or status: inspect as needed and give an evidence-backed answer."
- Итог первым. Все три ответа начинаются с «HTTP API бота слушает порт **55789**». Правило: "Lead with the outcome, not the steps you took to get there."
- Один вызов за ответ модели. Все 13 шагов с инструментом содержат ровно один вызов, хотя промпт требует параллельности. Правило: "When possible, parallelize independent tool calls rather than running them sequentially. This reduces round-trip latency and helps you get work done faster." Вывод: чтение `config.toml` и поиск сокетов можно было отправить вместе и сэкономить один цикл (1–2 с паузы на шаг).
- Первый найденный кандидат определяет ответ, альтернативы не проверяются. r2 с `*.py` нашёл `botApi.py`, r1 и r3 без `*.py` увидели только Rust. Правила: "Avoid over-formatting responses with bold emphasis, headers, lists, and bullet points." и "Remember that line numbers must NOT be included for non-codeblock citations (e.g. citing a filepath)."
