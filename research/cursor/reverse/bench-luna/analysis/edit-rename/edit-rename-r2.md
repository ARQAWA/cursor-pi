## edit-rename-r2
Итог: Агент получил задачу переименовать `record_wallet_failure` в `persist_wallet_failure` во всём проекте и сделал это за 8 ответов модели и 7 вызовов инструментов: rg ×2, ReadFile ×2, ApplyPatch ×2, Shell ×1. В каждом ответе был ровно один вызов, параллельных вызовов не было, субагентов и промежуточных сообщений тоже не было. Порядок был такой: найти все места, прочитать оба файла, поправить каждый файл патчем, повторить поиск, посмотреть diff и ответить. Изменены 2 файла и 5 мест (`failures.py`: 3, `login_sync.py`: 2). Повторный поиск старого имени ничего не нашёл, `git diff --check` вернул exit 0. По сути задача выполнена. Не сделано: тесты, импорт и линтер не запускались, а занятость нового имени агент не проверял (в текущей копии PycharmProjects `persist_wallet_failure` нет, а старое имя есть в тех же двух файлах). Порядок имён в импорте `login_sync.py` стал не алфавитным. Время: от первого запроса модели до последнего ответа 27.8 с, всего 37.5 с (около 8.5 с до первого запроса). Из 27.8 с подготовка запросов заняла 11.0 с, ответы модели 7.7 с, паузы между шагами 9.1 с (инструменты внутри них около 4.2 с). Токены: вход 83 655, из них из кэша 67 840 (81%), с шага 2 кэш покрывает 84–96% входа; выход 767; токены рассуждений 116, только на шагах 1, 2 и 4. Все ответы шли с одним ключом кэша.
### Шаг 1
Что: rg по корню проекта, шаблон `record_wallet_failure`, режим `content` (строки с номерами), лимит 200. Ответ модели 4.3 с, поиск 0.9 с.
Зачем: в задаче сказано «во всём проекте», а инструкция велит искать текст через `rg`: «prefer the dedicated search tools … (`rg`, `Glob`) over shell search commands». Сводка рассуждений: «Planning project-wide function renaming».
Принцип: перед массовой заменой сначала собери полный список мест, где встречается старое имя.
Результат: 5 совпадений в 2 файлах: `failures.py` строки 17, 47, 56 (два вызова и определение) и `login_sync.py` строки 15 (импорт) и 99 (вызов). Эти два файла агент читает дальше.
### Шаг 2
Что: ReadFile `failures.py` целиком, указан только путь. Ответ модели 3.2 с, чтение 0.1 с.
Зачем: номера строк уже известны, но описание ApplyPatch требует: «Make sure to read the file before applying a patch». Описание ReadFile советует читать файл целиком, а файл короткий (71 строка).
Принцип: перед правкой прочитай файл целиком, чтобы работать с его актуальным текстом.
Результат: строка 17 `retry_count = await record_wallet_failure(` в `record_controlled_failure`, строка 47 `await record_wallet_failure(` в `record_unexpected_failure`, строка 56 `async def record_wallet_failure(`. Номера совпадают с поиском. Сводка рассуждений: «Planning project-wide modification» (20 токенов).
### Шаг 3
Что: ReadFile `login_sync.py` целиком. Отдельный ответ модели без сводки рассуждений, чтение 0.1 с.
Зачем: это второй файл из результата шага 1. Агент читает его до патча по тому же правилу, что и на шаге 2. Вызовы шли по одному в разных ответах, хотя инструкция велит параллелить независимые вызовы; причина не видна, рассуждения зашифрованы.
Принцип: читай каждый файл, который собираешься менять, даже если номера строк уже известны.
Результат: импорт `record_wallet_failure` в строке 15 внутри `from superbot_ng.workers.wallet.failures import (`, вызов `await record_wallet_failure(` в строке 99 в ветке `except WalletRateLimitDefer` функции `_fetch_event`. Соседние `record_controlled_failure` и `record_unexpected_failure` — другие функции, в diff они не меняются.
### Шаг 4
Что: ApplyPatch, один файл `failures.py`, три блока `@@` без строк контекста: `retry_count = await record_wallet_failure(` → `persist_wallet_failure(`, ` await record_wallet_failure(` → `persist_wallet_failure(`, `async def record_wallet_failure(` → `async def persist_wallet_failure(`. Ответ модели 2.8 с, патч 0.5 с. Рассуждений 62 токена, сводка «Planning sequential patch application».
Зачем: строки уже известны из шага 2, поэтому правка точечная. Инструкция: «Try to use `ApplyPatch` for single-file edits». Описание ApplyPatch: «You must only include one file per call».
Принцип: правь файл точечным патчем по строкам, которые уже прочитал, по одному файлу за вызов.
Результат: «The file … has been updated.» В потоке 3 строки удалено и 3 добавлено, то есть ровно три совпадения из шага 1.
### Шаг 5
Что: ApplyPatch `login_sync.py`, два блока: `record_wallet_failure,` → `persist_wallet_failure,` в импорте и `await record_wallet_failure(` → `await persist_wallet_failure(` в вызове. Ответ модели 1.4 с, патч 0.6 с, рассуждений нет.
Зачем: та же схема, что на шаге 4. Строки 15 и 99 известны из шага 1 и прочитаны на шаге 3.
Принцип: повторяй проверенную схему для каждого файла и меняй только найденные места.
Результат: «has been updated», в потоке 2 строки удалено и 2 добавлено. Импорт теперь `record_controlled_failure, record_unexpected_failure, persist_wallet_failure`: порядок перестал быть алфавитным, агент это не исправил.
### Шаг 6
Что: rg с тем же шаблоном `record_wallet_failure` по всему проекту, режим `files_with_matches`. Ответ модели 1.5 с, поиск 0.4 с.
Зачем: задача «во всём проекте», поэтому после правок надо проверить, что старого имени не осталось. Агент проверил тем же шаблоном, что и на шаге 1.
Принцип: после правки повтори поиск по старому имени, чтобы убедиться, что его нигде нет.
Результат: «No files with matches found». Поиск учитывает `.gitignore` и `.cursorignore`, поэтому скрытые файлы не проверялись. Поиска нового имени `persist_wallet_failure` агент не делал ни до, ни после правки.
### Шаг 7
Что: Shell `git diff --check && git diff -- <оба файла>`, описание «Verify rename diff». Команда 1.7 с.
Зачем: оба ApplyPatch вернули только «has been updated», поэтому агент посмотрел фактический diff и проверил пробелы. Для git инструкция велит использовать Shell.
Принцип: перед отчётом посмотри реальный diff и проверь его на ошибки форматирования.
Результат: exit 0, то есть `git diff --check` ошибок не нашёл. В diff 5 блоков: `failures.py` 3, `login_sync.py` 2. Меняются только строки со старым именем, а соседние имена не трогаются.
### Шаг 8
Что: ответ без инструментов, тип «сообщение», ответ модели 1.5 с.
Зачем: вывод: все проверки дали нужный результат (поиск пуст, diff чистый, `git diff --check` exit 0), поэтому агент перестал вызывать инструменты. Инструкция: «Lead with the outcome, not the steps you took to get there».
Принцип: заканчивай, когда проверка подтвердила цель, и начинай отчёт с результата, без пересказа шагов.
Результат: «Переименовал `record_wallet_failure` в `persist_wallet_failure` во всём проекте. Проверка пройдена: старых упоминаний не осталось, `git diff --check` без ошибок.» Запуск завершился с exit 0 через 27.8 с после первого запроса.
