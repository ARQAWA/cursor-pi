## Алгоритм

Здесь r1, r2, r3 — прогоны edit-rename-r1, r2, r3. Во всех трёх агент шёл одной схемой. Отличается только последняя проверка.

1. **Поиск по всему проекту.** Один вызов `rg` с точным старым именем, режим `content`, `head_limit` 200, путь — корень рабочей папки (шаг 1 во всех трёх). Нашлось 5 строк в 2 файлах: `failures.py` (строки 17, 47, 56) и `login_sync.py` (строки 15, 99). Эти два файла становятся списком для чтения. Вопросов пользователю не задавалось, `AskQuestion` не вызывался.

2. **Чтение файлов целиком.** `ReadFile` каждого найденного файла без `offset` и `limit`: `failures.py` (1648 знаков), `login_sync.py` (3318 знаков). Цель — увидеть контекст вызовов, импорт и отсутствие алиасов (r1, сводка шага 2: «Planning project-wide renaming»). Файлы читаются по одному, в шагах 2 и 3. Они независимы, но вызовы не объединялись.

3. **Точечные патчи.** `ApplyPatch`, по одному вызову на файл. В `failures.py` три hunk'а: два вызова и определение функции. В `login_sync.py` два hunk'а: строка импорта и строка вызова в `_fetch_event`. Строк контекста нет, хотя описание инструмента предлагает по три строки до и после. Вывод: патчи сработали, потому что старый текст в каждом месте однозначен. Например, `    await record_wallet_failure(` с четырьмя пробелами не совпадает со строкой 17, где перед `await` стоит `retry_count =`. Ответ инструмента одинаковый: «has been updated». Новый текст он не показывает.

4. **Проверка.** Повторный `rg` по старому имени. В r1 и r2 это `files_with_matches` (шаг 6), в r3 `content` (шаг 6). Результат везде пустой. В r2 и r3 затем один `Shell`: `git diff --check && git diff -- <два файла>` (шаг 7). Код выхода 0, в diff ровно 5 изменённых строк. В r1 шага с diff не было.

5. **Остановка.** Когда проверка чистая, агент отвечает без инструментов: r1 на шаге 7, r2 и r3 на шаге 8. Условие одно: старое имя не найдено, а в r2 и r3 ещё и diff подтверждает замены. Ветки «нашлись остатки, вернуться к правке» в данных нет. Вывод: при остатках агент, вероятно, вернулся бы к шагу 3.

**Общее.** Везде один и тот же порядок из 6–7 вызовов и один вызов в каждом ответе. Промежуточных сообщений нет, финал единственный. Тестов и запуска кода нет. Новое имя не искалось ни разу.

**Различия.** r2 и r3 добавили diff, а r1 обошлась без него. r3 передала контекст в неверном параметре `-n -C` (шаги 1 и 6). Строк контекста в шаге 1 поэтому не было. На результат это не повлияло, потому что файлы читались целиком. Разница по времени в основном не в работе агента. Задержка до первого запроса менялась от 8,5 до 22,5 с (вывод: задержка харнесса). Собственный отрезок работы у r3 самый короткий, 26,5 с. Разница по кэшу: в r1 на шаге 2 кэш был 0, в r2 и r3 — 8960 (вывод: ключи префикса отличались, данными не объяснено). Вход растёт примерно на размер результата инструмента: 3318 знаков около 830 токенов, и на шаге 4 r1 вход вырос на 829.

**Качество.** По данным поиска всё переименовано: 5 вхождений в незаигнорированных файлах, diff содержит только эти строки, поведение не меняется. Не сделано или не проверено:
- Импорт в `login_sync.py` теперь не по алфавиту: `record_controlled_failure, record_unexpected_failure, persist_wallet_failure`. Ни один прогон этого не проверил. Вывод: линтер с проверкой порядка импорта может выдать замечание. Конфиг линтера не читался.
- Новое имя до правки не искалось, коллизия не проверена. Аналитический файл r2 пишет, что в копии PycharmProjects нового имени нет. Это вне данных прогона, не проверено.
- Код не компилировался, тесты не запускались. `git diff --check` ищет пробельные ошибки и маркеры конфликтов, но не синтаксис. В r3 на шаге 7 сводка рассуждения говорит «Verifying syntax and git diff», хотя команда синтаксис не проверяет.
- `rg` учитывает `.gitignore`, поэтому игнорируемые файлы не просматривались.
- Финальные ответы не говорят, что код не запускался. В них нет и списка изменённых файлов.

## Принципы

- **Сначала все места, потом правка.** Один поиск по корню проекта до первой правки (r1–r3, шаг 1). Правило: «When searching for text or files, prefer the dedicated search tools available to you (`rg`, `Glob`) over shell search commands.»
- **Читать файл целиком перед правкой, даже если номера строк известны.** r1–r3, шаги 2–3: номера уже были из шага 1, файлы всё равно читались. Правило из описания ApplyPatch: «Make sure to read the file before applying a patch to get the latest file content, unless you are creating a new file.»
- **Точечные правки, а не перезапись.** По одному файлу на вызов, для одного файла — `ApplyPatch` (r1–r3, шаги 4–5). Правила: «Try to use `ApplyPatch` for single-file edits, but use formatting commands for generated output and scripts for efficient bulk mechanical changes.» и «You must only include one file per call».
- **Проверять итог, а не статус инструмента.** `ApplyPatch` отвечал только «has been updated», поэтому r2 и r3 посмотрели diff (шаг 7). r1 остановилась на поиске (шаг 6). Правило: «Change or build: implement the requested change, verify it in proportion to risk, and hand off the completed result while a safe, relevant next step remains.»
- **Не расширять задачу.** Соседние функции `record_controlled_failure` и `record_unexpected_failure` не тронуты, тесты не добавлялись, порядок импорта не исправлялся (r1–r3). Правило: «Keep persistence inside the authorized scope. … an implementation into adjacent cleanup …»
- **Остановиться, как только цель подтверждена.** Последний ответ без инструментов сразу после чистой проверки (r1 шаг 7, r2 и r3 шаг 8).
- **Итог начинать с результата.** Все три финала начинаются с «Переименовал `record_wallet_failure` в `persist_wallet_failure` во всём проекте», затем одна-две фразы о проверке. Правило: «Lead with the outcome, not the steps you took to get there.»
- **Молчать по ходу, если нечего сообщить.** Ни в одном прогоне не было промежуточного текста, `assistantText` пуст до финала. Правило: «Do not send commentary merely because you are reading files, searching, running tools, thinking, about to edit, or because time passed.»
- **Shell только для того, что не делают специальные инструменты.** Файлы читались через `ReadFile`, правились через `ApplyPatch`, искались через `rg`. `Shell` появился только для git (r2 и r3, шаг 7). Правила: «If a tool exists for an action, prefer to use the tool instead of shell commands (e.g ReadFile over cat).» и описание Shell: «Use this tool for terminal operations like git, npm, docker, etc.»
- **Параллельность соблюдается не полностью.** Правило: «When possible, parallelize independent tool calls rather than running them sequentially.» В трёх прогонах не было ни одного ответа с двумя вызовами. Два независимых `ReadFile` шли в разных ответах.
