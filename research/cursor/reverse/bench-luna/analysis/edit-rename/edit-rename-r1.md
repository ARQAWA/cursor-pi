## edit-rename-r1
Итог: Агент получил одну задачу: переименовать `record_wallet_failure` в `persist_wallet_failure` во всём проекте. За 7 ответов модели он сделал 6 вызовов инструментов: rg ×2 (поиск старого имени до правок и после), ReadFile ×2 (оба файла, где имя нашлось) и ApplyPatch ×2 (по одному на файл). Изменил 5 строк в 2 файлах: в `failures.py` определение и два вызова, в `login_sync.py` импорт и один вызов. Финальный поиск ничего не нашёл, и агент ответил одной фразой по-русски. Субагентов не было. Время 42,8 с: модель 15,2 с, ожидание первого ответа модели 7,7 с, инструменты и паузы 6,2 с. Ещё 11,1 с до первого запроса и 2,5 с после последнего (вывод: это работа запуска и остановки харнесса). Токены: вход 71 879 (из кэша 46 848), выход 662, на рассуждения 123. Сводки рассуждений есть только у шагов 1, 2 и 4. Результат выполняет задачу по данным поиска: старого имени в рабочей копии не осталось (вывод: rg пропускает файлы из .gitignore). Не сделано: тесты, компиляция и линтер не запускались, новое имя на совпадения с существующими не проверялось. В импорте `login_sync.py` имя стоит не по алфавиту, после `record_unexpected_failure`, что может задеть линтер, если он проверяет порядок (вывод).
### Шаг 1
Что: rg по всей рабочей папке ищет текст `record_wallet_failure` и выводит строки с номерами (лимит 200).
Зачем: Пользователь попросил «во всём проекте», поэтому сначала нужно узнать, где имя встречается. Сводка рассуждений: «Planning function renaming with rg». Промпт: поиск текста через `rg` и `Glob`, а не через shell.
Принцип: Сначала найти все места, и только потом менять.
Результат: 4 строки в 2 файлах. `failures.py`: строки 17 и 47 (вызовы), 56 (определение). `login_sync.py`: строки 15 (импорт) и 99 (вызов). Эти два файла агент читает дальше.
### Шаг 2
Что: ReadFile `failures.py` целиком (70 строк).
Зачем: rg показал только строки, без контекста. Сводка: «Planning project-wide renaming». Нужно было увидеть, кто вызывает функцию и есть ли алиасы или другие имена.
Принцип: Перед правкой читать файл целиком. Описание ApplyPatch требует: «Make sure to read the file before applying a patch».
Результат: Вызовы в `record_controlled_failure` (строка 17) и `record_unexpected_failure` (строка 47), определение в строке 56, алиасов нет. Обёртки `record_controlled_failure` и `record_unexpected_failure` не содержат имя `record_wallet_failure`, поэтому не меняются.
### Шаг 3
Что: ReadFile `login_sync.py` целиком.
Зачем: rg показал импорт (строка 15) и вызов (строка 99). Агенту нужен импортный блок и контекст вызова. Сводки нет.
Принцип: Читать каждый файл с совпадением до правки. Независимые чтения лучше делать одним ответом (промпт: «When possible, parallelize independent tool calls»). Модель читала по одному файлу за ответ (вывод: этот файл можно было прочитать вместе с `failures.py` на шаге 2).
Результат: Импорт из `superbot_ng.workers.wallet.failures` содержит три имени: `record_controlled_failure`, `record_unexpected_failure`, `record_wallet_failure`. Вызов в `_fetch_event` (строка 99) стоит внутри `except WalletRateLimitDefer`.
### Шаг 4
Что: ApplyPatch для `failures.py`: один патч с тремя правками, двумя вызовами и определением.
Зачем: Файл уже прочитан на шаге 2, все три места известны. Промпт: «Try to use `ApplyPatch` for single-file edits». Сводка: «Planning sequential single-file renaming».
Принцип: Для правок в одном файле делать один точечный патч, а не переписывать файл целиком.
Результат: Ответ «has been updated». Все три места в `failures.py` теперь `persist_wallet_failure`. Строк контекста в патче нет, строки найдены по тексту.
### Шаг 5
Что: ApplyPatch для `login_sync.py`: строка импорта и строка вызова.
Зачем: Это второй файл из шага 1, прочитан на шаге 3. Сводки нет. Правило инструмента: «You must only include one file per call», поэтому отдельный патч на файл.
Принцип: Один файл, один патч, по уже прочитанному тексту.
Результат: Ответ «has been updated». Имя в импорте стоит последним, после `record_unexpected_failure`, порядок по алфавиту не восстановлен.
### Шаг 6
Что: rg по всей рабочей папке в режиме «только имена файлов» ищет `record_wallet_failure` ещё раз.
Зачем: Пользователь просил «во всём проекте», поэтому после правок нужна проверка, что старого имени не осталось. Сводки нет. На шаге 1 нашлось 2 файла, и оба уже исправлены.
Принцип: После замены заново искать старое имя, чтобы убедиться, что ничего не пропущено.
Результат: «No files with matches found». Старого имени в рабочей копии нет (вывод: rg пропускает файлы из .gitignore).
### Шаг 7
Что: Ответ без инструментов: одна фраза по-русски с результатом.
Зачем: Задача выполнена, поиск подтвердил отсутствие старого имени, дальнейших действий не нужно. Сводки нет.
Принцип: Сделать изменение и проверить его в объёме, соразмерном риску, затем отдать готовый результат (промпт: «implement the requested change, verify it in proportion to risk, and hand off the completed result»).
Результат: «Переименовал `record_wallet_failure` в `persist_wallet_failure` во всём проекте. Старых упоминаний не осталось.» Проверка только поиском, без запуска кода и тестов.
