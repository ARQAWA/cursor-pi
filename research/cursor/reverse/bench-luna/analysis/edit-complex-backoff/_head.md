## Алгоритм

1. **Разведка.** Все три прогона начали с поиска по счётчику. r1: Glob `*` (шаг 2), шумный rg `retry_count|wallet|sync` (шаг 3), точный rg `retry_count` (шаг 4). r2: один rg по всему репозиторию (шаг 1). r3: Glob (шаг 1), rg по четырём словам (шаг 2). Все нашли миграцию `000007_wallet_sync.sql:38`, `store.rs:69` и `84` и Python-файлы.
2. **Обе реализации.** Python: `failures.py` передаёт фиксированные 30 с, `store_sync_results.py` считает `next_attempt_at = now + max(1, retry_after_seconds)`, `store_sync_failure_sql.py` увеличивает счётчик и возвращает его. Rust: `WalletStore::record_failure` в `store.rs`, вызовы в `daemon.rs`. Что реально работает в проде, показал `docker-compose.app.yml`: сервис `wallet_sync` запускает `/app/wallet-sync`. Так проверили r1 (шаг 15) и r3 (шаг 17). В анализе r2 такой проверки нет, и она правила оба контура.
3. **Тесты.** Все три прочитали `tests/contracts/wallet/test_wallet_failure_contracts.py`. Первый тест (строка 10) проверяет возврат `retry_count` и подстроку `RETURNING retry_count`.
4. **Где менять.** Все три пришли к одной идее: счётчик растёт в том же UPDATE, поэтому задержку можно считать в SQL из старого значения. Тогда 30 × 2^(старое) равно 30 × 2^(новое − 1). Потолок: `CASE` у r1, `LEAST(…, 6)` у r2 и r3. Вывод: арифметика сходится. Субагент предлагал считать в Python после RETURNING, но r1 выбрала SQL (шаг 25).
5. **Правка.** Четыре файла: `store.rs`, `store_sync_failure_sql.py`, `store_sync_results.py` (расчёт в Python убран) и тест. SQL переписывали по нескольку раз. r1: по четыре правки в каждом SQL-файле (Python: шаги 25, 34, 44, 55; Rust: 28, 35, 45, 56). r2: от двух запросов к одному и потолок степени 9 сменила на 6 (шаги 20, 24, 26). r3: тот же переход за шаги 20–28.
6. **Проверка.** `uv run pytest` на тест-файле: 1 прошёл, 8 упали на `No module named '_superbot_native'`. `cargo check -p superbot-wallet-sync` из `rust/` прошёл у всех трёх. SQL на PostgreSQL не запускал никто.
7. **Ремонт.** Неверный путь к файлу вывода или папка исправлялись и повторялись (r1 шаги 39–42, r2 шаги 35–36 и 43–46, r3 шаги 37–38). Два патча упали из-за номеров строк `10|` или пустой строки в контексте (r2 шаг 21, r3 шаги 22 и 29). r1 опрашивала AwaitShell восемь раз, пять раз процесс ещё работал.
8. **Остановка.** Все три закончили текстом без инструментов после последней проверки. В каждом прогоне два текста подряд (r1 шаги 64–65, r2 57–58, r3 52–53).

**Субагент (только r1).** После ручного чтения (шаги 1–12) r1 вызвала `CallDynamicTool → Subagent` (шаг 13): тип `explore`, модель `inherit`, без фона. Причину агент записал так: вопрос широкий и охватывает два языка, нужны «точное место вставки и список неоднозначностей». Задание: найти все реализации и тесты, «Do not edit files», вернуть неоднозначности Python и Rust. Ответ: Python — расчёт после RETURNING в `WalletSyncResultMixin.record_failure()`; Rust — нужна правка SQL или два шага; неясен приоритет задержки Steam 429. Работа субагента: 16 ответов, 15 вызовов (ReadFile 10, rg 3, Glob 2), 292 360 токенов, модель 35 с, пауза 16 с. Родитель видел вызов как 74 с и вопрос про 429 пользователю не задал.

**Общее и различия.** Общее: одни и те же четыре файла, одна формула в одном UPDATE, `_retry_seconds` в Rust, подстрочные проверки в тесте, один и тот же тупик с `_superbot_native`. Вывод: один поиск по `retry_count` приводит к одним местам, а требование сводится к одной формуле. Различия:
- r1 единственная запускала субагента и проверила прод. Она самая быстрая (441 с). Модельное время у неё ниже (184 с против 395–435 с), причина по данным не видна.
- r2 прод не проверяла, сделала 11 правок, в том числе сменила потолок степени. Ruff упал, разобрана только видимая часть.
- r3 прод проверила. Оставила функцию `wallet_failure_retry_seconds` в Python, которую рабочий путь не вызывает, а тест вызывает. Импорт `timedelta` не убрала, вывод: он стал неиспользуемым. Видела `backoff_delay_seconds` в `inventory_seller` (база 30 с, потолок 900 с, `daemon.rs:35`), но не открыла её.

**Качество относительно задачи.**
- Формула верна во всех трёх: 30, 60, 120, 240, 480, 960, далее 1800 с (вывод: проверка арифметики по коду). Существующий `retry_count` используется.
- Тесты обновлены только подстроками SQL. Значения не проверяет ни один тест, кроме r3, а её функция в прод-пути не участвует.
- Побочный эффект не назван ни в одном финале: задержка Steam 429 (`retry_after_seconds`) и `failure_retry_seconds` из `config.toml` больше не влияют на расписание. Видно по diff всех трёх.
- Не проверено (вывод): выражение `$k + … INTERVAL` во всех трёх может не определить тип параметра `$k` в PostgreSQL и отклонить запрос. Риск отмечен только в анализе r2.

## Принципы

- **Режим «Change or build».** Правило: "Change or build: implement the requested change, verify it in proportion to risk, and hand off the completed result while a safe, relevant next step remains." Компиляция Rust и тест-файл проверены во всех трёх (r1 шаг 62, r2 шаг 51, r3 шаг 46), SQL на PostgreSQL не проверен ни в одном. Проверка не соответствует риску SQL (вывод).
- **Параллельные вызовы.** Правило: "When possible, parallelize independent tool calls rather than running them sequentially." Во всех трёх по одному вызову в ответе. Например, r1 шаги 5–11 читают шесть файлов и один rg, каждый в своём ответе.
- **Инструменты вместо shell.** Правила: "When searching for text or files, prefer the dedicated search tools available to you (`rg`, `Glob`) over shell search commands." и "If a tool exists for an action, prefer to use the tool instead of shell commands (e.g ReadFile over cat)." Поиск шёл через rg и Glob (r1 шаги 2–4, r2 шаг 1, r3 шаги 1–2), чтение через ReadFile (21–25 раз), shell только для git, pytest и cargo.
- **Номера строк в патче.** Правило: "Treat the "Lxxx:" prefix as metadata and do NOT treat it as part of the actual code." В выдаче этих прогонов номера шли как `N|`, не как `Lxxx:`. Из-за них упали патчи r2 шаг 21 и r3 шаг
29. Агенты убрали номера и повторили (r2 шаг 22, r3 шаг 30).
- **AwaitShell.** Правило из описания инструмента: "Prefer NOT to poll reflexively with AwaitShell." Опрос допустим, если "Your very next step is blocked on this specific job's result". r1 опрашивала восемь раз (шаги 32, 38, 47, 48, 52, 53, 59, 62), пять раз процесс ещё работал, между опросами читала файл терминала (шаги 33, 40, 49). r2 (шаги 49–50) и r3 (шаги 41, 43) опрашивали, потому что следующий шаг ждал сборку.
- **Ремонт после сбоя.** Правило: "Transient technical friction: retry or use a relevant alternative." Неверный путь или папка исправлялись за один-два шага: r1 шаги 39→40 и 41→42, r2 шаги 35→36 и 44→46, r3 шаги 37→38.
- **Проверка утверждений.** Правило: "Verify uncertain claims. When a claim is wrong or risky, say so directly and explain the technical reason." Все три назвали восемь падающих тестов «окружением» и не проверили их на исходном коде (r1 шаг 60, r2 шаг 58, r3 шаг 27). Эффект для Steam 429 не назван ни в одном финальном ответе (r1 шаг 65, r2 шаг 58, r3 шаг 53).
- **Один ответ.** Правила: "Lead with the outcome, not the steps you took to get there." и "The user should not have to read your message twice." В каждом прогоне два текста подряд (r1 шаги 64–65, r2 57–58, r3 52–53).
- **Субагент только для широкого вопроса.** Описание Subagent: "If the query is a narrow or specific question, you should NOT use the Subagent and instead address the query directly using the other tools available to you." r1 сначала прочитала это описание (шаг 1), потом вызвала субагента для широкого вопроса по двум языкам (шаг 13). Вопрос, который субагент поднял (приоритет 429), пользователю не передан.
