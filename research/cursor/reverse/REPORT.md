## Ограничения данных

Адаптер искажает два места, и выводы о скорости это учитывают.

- Адаптер отправляет в ChatGPT `parallel_tool_calls=false`, хотя Cursor просит параллельные вызовы. Поэтому во всех 797 ответах не больше одного вызова инструмента. В родном Cursor та же модель группирует независимые чтения и поиски, и шагов было бы меньше.
- Адаптер узнаёт разговор по его началу. У субагентов одного чата начало одинаковое (системный промпт и служебный блок), поэтому все они попали в одну сессию адаптера, а она обслуживает запросы по одному. В 159ffaa4 два фоновых субагента работали одновременно, и их пауза между шагами выросла до 2,2–2,8 с против обычных 1,0–1,3 с, с провалами до 52 с.

Кроме того, в 81d2a5dd клон уже содержал правки sales_history от прошлого прогона (`git_status` в [служебном блоке](prompts/items/context-67caf0cc4755.md)), а на шаге 12 агент искал в транскриптах прошлых чатов текст задачи и seed. Качество решений и сравнение с эталоном в этот разбор не входят.

## Из чего состоит запрос

Каждый запрос Cursor — это полный разговор с начала, без `previous_response_id`. Первые три элемента у всех агентов одни и те же:

1. [Системный промпт](prompts/items/system-04c3f59902ee.md), около 15 500 символов. Он общий для всех задач и всех ролей; у Luna отличается только именем модели, у субагентов Sol в 38083b08 нет одной строки про картинки. Правила сбора контекста в нём короткие: искать через `rg` и `Glob`, а не оболочкой; читать через ReadFile; параллелить независимые вызовы; не печатать разделители `echo "===="`. Остальное — режимы запроса (ответ, диагноз, правка), автономия в границах запроса, редкие обновления и короткий финал.
2. [Служебный блок](prompts/items/context-a89a85ce8dba.md), около 21 500 символов: ОС и workspace, пути к хранилищам и транскриптам, типы субагентов, модели, список skills Cursor и каталог динамических неймспейсов (браузер, origin, subscriptions, cursor). Подписи skills и неймспейсов занимают большую часть блока.
3. Запрос пользователя с меткой времени.

Набор инструментов main — восемь функций: Shell, Glob, rg, ReadFile, ApplyPatch, AskQuestion, GetDynamicTools, CallDynamicTool ([toolset](prompts/tools/toolset-bb31022a144f.json)). Всё остальное (Subagent, TodoWrite, SwitchMode, WebSearch, Delete и другие) спрятано: модель видит только имена в каталоге и загружает схему через GetDynamicTools, а вызывает через CallDynamicTool. Так 14 редких инструментов не занимают место в каждом запросе, а полная схема Subagent (9 464 символа) появляется в разговоре один раз, когда нужна.

Описания основных инструментов задают механику сбора контекста:

| Инструмент | Что задаёт описание | Что видно в выводе |
|---|---|---|
| Glob | шаблон без `**/` дополняется до рекурсивного, результат по времени изменения, «делай несколько поисков пачкой» | шапка `total N files`, список обрывается около 5 000 символов строкой `... K more files ... (Do a more specific search if needed)` |
| rg | ripgrep с .gitignore, `type` лучше широкого `glob`, режимы content/files/count, `head_limit` | `<workspace_result>`, файлы с номерами строк; при обрыве `[Results truncated. Showing 197 of at least 1062 matching lines. Use offset=197 ...]`; большой вывод около 15 000 символов |
| ReadFile | «лучше читать весь файл без offset и limit», «читай несколько файлов пачкой» | файл целиком, номер у каждой десятой строки (`    10\|`) |
| ApplyPatch | один файл за вызов, grammar-формат, абсолютные пути | короткое подтверждение, около 120 символов |
| Shell | не для чтения и поиска, не обрезать вывод `head`/`tail`, большой вывод уходит в файл терминала | в этих чатах Shell не вызывался ни разу |

## Цикл 1: глубокий поиск

Так работали 38083b08 и 704ada44: пользователь просит изучить три модуля и написать отчёт, запускать ничего нельзя.

1. Main сразу делегирует. Sol на первом шаге загружает схему Subagent и запускает субагента по первому модулю; Luna сначала переключается в режим Plan, делает один Glob и один rg по корню, потом делегирует. Ни Sol, ни Luna не изучают код сами до делегирования.
2. На каждый модуль — один субагент с брифом 700–1 000 символов: путь к репозиторию, запрет менять и запускать, модуль, перечень того, что найти (точки входа, модели, конфиг, фоновые процессы, тесты), требуемая тщательность и форма ответа — самодостаточное описание на русском ([брифы](prompts/items/), файлы `subagent-task-*`).
3. Субагент получает тот же системный промпт, урезанный служебный блок и свой `system_reminder`. Для explore это роль [«file search specialist … fast agent»](prompts/items/subagent-task-33666c41b589.md): быстро искать Glob и rg, читать файлы, параллелить grep и чтения, абсолютные пути в отчёте, `UpdateCurrentStep` для строки прогресса у родителя. Explore не может звать субагентов: у него нет Subagent в каталоге.
4. Ход субагента одинаковый во всех шести случаях: `UpdateCurrentStep`, широкий Glob (`**/*.py`, `*`), один или несколько широких rg с длинной альтернацией терминов и `head_limit`, затем чтение найденных файлов целиком по одному. ReadFile составляет 52–91% вызовов ([coverage/requests.md](coverage/requests.md)). Субагент пишет итог обычным сообщением.
5. Main получает только итог: [«This is the output of the subagent»](prompts/items/dyn-CallDynamicTool-bc2f0c22ef21.md), короткую сводку `user_visible_high_level_summary`, полный ответ (16–32 тыс. символов) и Agent ID для `resume`. Ход субагента, его чтения и поиски в контекст main не попадают.
6. Sol запускал субагентов блокирующими, по одному; следующий запускал после результата предыдущего. После трёх результатов Sol одной `ApplyPatch` Add File записал отчёт (12 137 токенов за 147 с), прочитал его начало и поправил одну строку. Luna после субагентов ещё 35 шагов перечитывала код: 29 из 31 файла субагенты уже читали. Затем тоже записала отчёт одной `ApplyPatch` (17 853 токена за 148 с).

Время Sol-цикла (844 с): 613 с — три субагента по очереди, 147 с — генерация отчёта, остальное — 13 коротких шагов main. Luna (2 525 с): 2 158 с — субагенты, около 150 с — перечитывание, 148 с — отчёт.

## Цикл 2: задача с правкой кода

Простая задача (81d2a5dd) решалась без субагентов, за 40 шагов и 496 с.

1. rg по каталогу `rust` в режиме files, затем rg по сервису в режиме content с альтернацией ключевых слов.
2. Чтение крупных диапазонов найденных файлов: `daemon.rs` строки 1–640, `steam.rs` 1–360, `lib.rs` 200–390. Всего 9 чтений 5 файлов; чтения целиком — одно.
3. Узкие rg в content для каждого символа, который понадобился: `enum SellOutcome`, `SellOutcome::`, таблица guard в миграциях, `pub struct Asset`.
4. 14 небольших `ApplyPatch` в трёх файлах вперемешку с точечными rg и чтениями коротких диапазонов вокруг правки. Сборки и тестов не было: их запретил запрос.
5. Отчёт одной `ApplyPatch`, финальный ответ.

Контекст main вырос с 12 до 44 тыс. токенов. Медиана генерации шага — 6,7 с, выше, чем у поисковых шагов, потому что здесь модель пишет патчи.

Сложная задача (159ffaa4) — смешанный цикл. Main запустил двух explore-субагентов в фоне (старый Python и Rust-сервис), получил ответ [«работай дальше, результат придёт сам»](prompts/items/dyn-CallDynamicTool-ba33db969ab6.md) и параллельно сам прошёл тот же путь: 27 чтений, 13 rg, затем правки `steam_client.rs` и отчёт. Результаты субагентов пришли [уведомлением](prompts/items/notification-62429f237a07.md) только после финала main: Cursor доставляет их, когда агент заканчивает ход. Main дописал ещё одну правку `steam_session.rs` и дополнил отчёт. 18 из 23 файлов, которые main прочитал сам, читали и субагенты.

## За счёт чего быстро

- Короткий шаг. Медиана: 0,07–0,18 с адаптер, 0,7–0,9 с до первого токена, 0,9–1,8 с генерация на поисковом шаге, 1,0–1,3 с исполнение инструмента и отправка следующего запроса Cursor. Поисковый шаг субагента занимает около 3 с ([таблицы в sessions/](sessions/)). Рассуждения на таких шагах почти нет: у explore Sol 100–1 400 токенов рассуждения на 25–49 шагов.
- Роль explore работает на сниженном усилии. Main Sol шёл на medium, его explore-субагенты — на low при `model: inherit`. Luna generalPurpose шли на xhigh, как main, и читали в 4 раза больше файлов (153/114/118 против 18/36/30).
- Кэш. 94,6–97,8% входных токенов взяты из кэша: начало разговора (системный промпт, служебный блок, запрос) не меняется, а история только дописывается в конец.
- Контекст в субагентах. Субагент Sol заканчивает работу с 36–50 тыс. токенов входа, main глубокого поиска — с 48 тыс. Компакшенов не было ни у одного из 12 агентов: число элементов входа у каждого только растёт. Luna-субагенты дошли до 160–185 тыс. и тоже без компакшена.
- Отчёт пишется за один проход: один вызов ApplyPatch Add File на весь документ.
- Задачу без субагентов модель решает узкими rg в режиме content и чтением больших диапазонов вокруг найденного, без повторного чтения целых файлов.

## Где Cursor теряет время

- Блокирующие субагенты по очереди (38083b08, 704ada44): три независимых модуля исследовались последовательно, хотя Subagent поддерживает `run_in_background`.
- Повторная работа main после субагентов: Luna перечитала 29 файлов, которые уже разобраны в отчётах субагентов; в 159ffaa4 main повторил работу фоновых субагентов вместо ожидания их результата.
- Один вызов на шаг из-за адаптера (см. «Ограничения данных»); в родном Cursor эту потерю снимают параллельные вызовы.
- Служебный блок на 21,5 тыс. символов в каждом разговоре, в основном подписи skills и MCP-неймспейсов, которые в этих задачах не понадобились. Кэш снимает цену повторов, но не первого запроса.

## Сравнение сессий

| Показатель | Sol, глубокий поиск | Luna, глубокий поиск | Sol, сложная | Sol, простая |

| Время, с | 844 | 2 525 | 502 | 496 |
| Шагов main / субагентов | 13 / 119 | 46 / 456 | 58 / 65 | 40 / 0 |
| Чтений (уникальных файлов) | 87 (76) | 417 (260) | 62 (39) | 9 (5) |
| rg / Glob / ApplyPatch | 17 / 9 / 2 | 30 / 25 / 1 | 31 / 8 / 9 | 16 / 0 / 14 |

Sol и Luna получили одинаковые промпты, но Luna на xhigh и с generalPurpose-субагентами прочитала в 3,4 раза больше разных файлов, а main Luna вдобавок перечитал код за субагентами. Разница во времени объясняется объёмом чтения и числом шагов, а не скоростью модели: медианы шага у них близки.

## Что перенести в my-omp-harness

| Приём Cursor | Доказательство | Как перенести и улучшить |
|---|---|---|
| Отдельная роль быстрого поиска на сниженном усилии, которая не может делегировать дальше | [explore-задача](prompts/items/subagent-task-33666c41b589.md), усилие low при main medium, [урезанный блок](prompts/items/context-b315a735c81c.md) | Держать `enot` для поиска на низком усилии, без права звать агентов; уровень брать ниже, чем у Main |
| Бриф субагенту: путь, запреты, что найти, тщательность, форма ответа, 700–1 000 символов | брифы в `prompts/items/subagent-task-*` | Уже есть в brief-правилах; добавить явный уровень тщательности (quick/medium/very thorough) |
| Main получает только итог субагента, без хода | [результат субагента](prompts/items/dyn-CallDynamicTool-bc2f0c22ef21.md) | Так уже работает `task`; удержать отчёт субагента в 16–32 тыс. символов и запрет пересказывать ход |
| Независимые модули — отдельным субагентам | 38083b08, 704ada44 | Улучшить: запускать их одной волной параллельно, а не по очереди, как Cursor |
| Не перепроверять отчёт субагента чтением тех же файлов | Luna: 29 из 31 файла повторно; 159ffaa4: 18 из 23 | Правило для Main: после отчёта субагента читать только то, чего в отчёте нет и что нужно для правки |
| Фоновый субагент и продолжение своей работы | [уведомление](prompts/items/notification-62429f237a07.md) | Улучшить: не делать финал до результата фоновых субагентов, если результат нужен ответу; в 159ffaa4 финал вышел раньше данных |
| Редкие инструменты за каталогом, схема по запросу | GetDynamicTools, каталог в служебном блоке | В omp совпадает с отложенными инструментами; держать в каждом запросе только read/glob/rg/edit/bash/task |
| Вывод поиска с жёстким потолком и строкой продолжения | Glob около 5 000 символов, rg около 15 000 с `Use offset=` | Уже повторено в `extensions/rg.ts`; сверить потолки с этими цифрами |
| Чтение целиком для поиска, большими диапазонами для правки | субагенты: 52–91% вызовов — чтение, почти всё целиком; 81d2a5dd: диапазоны 190–640 строк | В `context-gathering` развести два режима: исследование — файлы целиком пачкой; правка — rg по символу и диапазон вокруг |
| Отчёт одной записью | ApplyPatch Add File на 12–18 тыс. токенов | Уже есть правило «большой документ за один проход» |
| Стабильное начало разговора | кэш 94,6–97,8% | Не вставлять в начало промпта меняющихся данных; служебный блок держать коротким |
| Строка прогресса субагента для родителя | `UpdateCurrentStep` | Аналог — `progress`; для субагентов не обязателен |

Параллельные вызовы в одном шаге и параллельные субагенты в Cursor есть, но в этих данных их не видно из-за адаптера. Их эффект по этим журналам не измерен.
